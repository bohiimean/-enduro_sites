## Контекст

Сайт — витрина того же бизнеса, что и бот: продажа эндуро-мотоциклов в Москве и продажа юаня за рубли. Бот закрывает сценарии в Telegram, сайт должен закрыть то же самое в вебе **и добавить то, чего в боте нет: админку и личный кабинет**.

Нагрузка того же порядка, что у бота (десятки человек в час). Django + PostgreSQL выбраны **не из-за нагрузки**, а из-за двух требований, которых Google Sheets не закрывает: управляемая админка для каталога/курса/заказов и хранение состояния платежей, переживающее рестарт.

### Чем сайт принципиально отличается от бота

Это не перенос один в один. Четыре вещи на сайте объективно лучше, и ради них стоит отступать от решений бота:

1. **Настоящий `payer_ip` и `User-Agent` плательщика.** У бота их нет — Telegram не отдаёт IP пользователя, и туда шлётся IP сервера (костыль, согласованный с поддержкой alfabit). Антифрод alfabit на сайте заработает как задумано. Поля `payer_user_agent` / `payer_device_id` в клиенте уже есть, просто не заполнялись.
2. **Состояние платежа в БД.** У бота `_pending` — dict на 500 записей в памяти, `payment_uid` зашит в `callback_data`, всё теряется при рестарте.
3. **Кнопка «✅ Я оплатил» не нужна.** Фронт опрашивает наш API, бэкенд фоном опрашивает alfabit.
4. **KYC-наблюдение переживает рестарт.** У бота `KycWatcher` держит заявки в памяти; разбор случая 16.08.2026 — клиент двое суток считал, что верификация зависла.

### Чего сайт НЕ делает

- Не выдаёт юань автоматически. Как и бот: alfabit закрывает только **приём рублей**, выдачу делает менеджер после подтверждения оплаты.
- Не продаёт байки онлайн. Каталог — просмотр и заявка менеджеру.

## География размещения (решено, это жёсткое ограничение)

| Компонент | Где | Почему так, а не иначе |
|---|---|---|
| Сайт (Django, PostgreSQL, Nuxt, worker) | **РФ** | персданные граждан РФ — 152-ФЗ требует локализации |
| Telegram-бот | **зарубежный VPS** | Telegram заблокирован в РФ, сервер физически не достучится до `api.telegram.org` |
| `rate-service` (скрапер) | **зарубежный VPS** | investing.com за Cloudflare, с российского IP скрапится хуже; плюс живёт рядом с ботом |

Из этого следует правило, которое нельзя нарушать:

> **В запросе пользователя сайт за границу не ходит. Никогда.**

Скрап investing занимает 2–3 минуты, канал через границу нестабилен, и первый же таймаут превращает страницу курса в спиннер. Тянет данные фоновый `worker` по расписанию и кладёт в PostgreSQL вместе с `fetched_at`; API всегда отвечает из БД. Протухшие данные отдаём с пометкой времени, а не ошибкой — так уже сделано в боте (`bot/handlers/rates.py`, `_TTL_STALE_WARN`).

```
[зарубеж]  rate-service  (FastAPI + Chromium + APScheduler)
                 ↑ pull по расписанию, HTTPS + токен + IP allowlist
[РФ]       worker (Django ORM) ──→ PostgreSQL ──→ DRF API ──→ Nuxt
```

`rate-service` наружу не публикуется: доступ по статическому токену в заголовке плюс allowlist по IP российского сервера.

## Функционал

### 1. Курс валют

Публичная страница: цена юаня по каждому способу оплаты. Переносится из `bot/handlers/rates.py`.

Три независимых источника котировок:

| ключ | источник | как достаётся | наценка |
|---|---|---|---|
| `usdt_rub` | Rapira, `GET api.rapira.net/open/market/rates`, пара `USDT/RUB`, поле `close` | обычный HTTP | `× 1.045` |
| `usd_rub` | investing.com `/currencies/usd-rub` | **SeleniumBase + headless Chromium, 2–3 мин** | прибавка в рублях, см. ниже |
| `usdt_rub_alfabit` | внутренний API витрины alfabit, `/wallet-web/api/v1` | HTTP, комиссия метода читается на лету | `× 1.0175` |

Фолбэк `usd_rub`: investing → TwelveData (`FallbackProvider`). Подключается, только если задан `TWELVEDATA_API_KEY`.

**Витрина alfabit считается в два шага** (`bot/services/rate_providers/alfabit.py`, там же обоснование): `rate_effective` из `/public/fiat-converter/rate` × `(1 + deposit_fee_percent/100)` метода `SBPRUB` из `/public/buy-sell/banks/RUB`. Комиссия **не зашита в код** — читается при каждом обновлении, чтобы цена ехала за кабинетом сама. Если список банков недоступен — берётся последняя известная комиссия; если её ещё нет — курс не отдаётся вовсе (считать без комиссии нельзя, это тихо уронит цену на 1.8%).

**Цена юаня = курс / 6.63.** Делитель один на всё — и на витрину, и на сумму платежа (`bot/services/yuan.py`). Прод считает по 6.63, не менять без явного запроса.

**Два разных типа наценки** — одним полем в модели не обойтись:

- коэффициент: `курс × 1.045` (Rapira, alfabit);
- прибавка в рублях к курсу USD/RUB: `(курс + 2.6) / 6.63` (наличные в Москве).

Уровни для наличных (`bot/services/usd_markup.py`), прибавка в рублях:

| уровень | будни | выходные |
|---|---|---|
| Стандарт | 2.6 | 2.7 |
| от 300 000 ₽ | 2.1 | 2.5 |
| от 500 000 ₽ | 1.7 | 2.1 |
| от 1 000 000 ₽ | 1.5 | — |

### 2. Оплата: QR + KYC через Alfabit

Приём рублей по СБП с верификацией плательщика. Alfabit выступает эквайером: генерирует QR/реквизиты СБП, принимает рубли на баланс аккаунта, KYC сверяет ФИО плательщика с отправителем перевода. Документация: `https://alfabit.org/ru/api-docs`.

**Авторизация.** HMAC-SHA256, заголовки `X-API-Key` / `X-API-Signature` / `X-API-Timestamp`, где `message = "{timestamp}{METHOD}{path}{body}"`, timestamp живёт 5 минут. Боевой клиент со всеми выстраданными деталями — `bot/services/alfabit/client.py`, переносится в Django почти дословно (см. «Что переносим из бота»).

**Эндпоинты:**

| метод | назначение |
|---|---|
| `GET /api/v1/integration/converter/fiat/rate` | курс USDT/RUB со спредом alfabit (запасной путь к курсу витрины) |
| `POST /api/v1/integration/checkout/payments` | создать RUB-платёж; при непройденном KYC вернёт `status=kyc_required` |
| `GET /api/v1/integration/checkout/payments/{uid}` | статус платежа + `qr_url` / `qr_payload` |
| `GET /api/v1/integration/checkout/payers/{phone}` | статус KYC: `not_started` / `pending` / `approved` / `rejected`, `expected_payer_name` |
| `POST /api/v1/integration/checkout/payers/{phone}/documents` | загрузка документа, multipart |

**Порядок шагов сознательно не такой, как в доках alfabit:** телефон → KYC → сумма → создание платежа → QR. В доках платёж создаётся первым и возвращает `kyc_required`, но тогда зафиксированный курс жил бы весь KYC, а верификация может уйти на ручную сверку — это не секунды. Окно фиксации курса должно быть «от QR до оплаты», то есть минуты.

**Три разных `pending`** различаются по полям ответа и звучат для пользователя по-разному:

- `processing=true` — идёт распознавание;
- `manual_review=true` — заявку забрал оператор, **переотправка тех же файлов запрещена докой**;
- всё остальное — ждём от человека недостающий документ.

**Вебхука на смену статуса KYC у alfabit нет** — в доке сказано прямым текстом, только опрос. Про вебхук на **платёж** надо уточнить отдельно: у бота его не было принципиально (не хотели nginx), у сайта HTTPS и так есть — см. «Открытые вопросы».

**Документы:** `passport_main` + `passport_registration`. Признак «распозналось плохо» (`low_confidence`) приходит **только в ответе на загрузку**, в `GET /payers` его нет — второго шанса увидеть не будет, обрабатывать сразу.

**Лимиты (показывать пользователю до ввода суммы):** не больше 100 000 ₽ за операцию и не больше 100 000 ₽ в сутки суммарно.

### 4. Личный кабинет

Новая сущность, в боте отсутствует. История заказов, статус KYC («верифицированы — повторно документы не нужны»), история платежей, статус поставки.

**Логин — почта + пароль** (`USERNAME_FIELD = email`, решено 26.09.2026; отменяет решение от 22.09.2026 о телефоне как логине).

Причина смены одна: **опора аккаунта должна проверяться бесплатно.** Телефон подтверждать нечем — каналов нет, SMS платные, — а при телефоне-логине ворота из следующего раздела закрывают в кабинете всё. То есть кабинет нельзя было запустить, не заплатив сначала за SMS. Почта проверяется письмом со ссылкой и заодно закрывает восстановление пароля.

Довод от 22.09.2026 против почты («ключ KYC у alfabit — номер, получатся две идентичности, придётся сшивать руками») снят так: **номер остаётся ключом KYC**, `Payer` по-прежнему уникален по телефону, аккаунт держит только ссылку на него. Меняется исключительно то, чем открывается дверь. Сшивать нечего — связь аккаунт↔плательщик это FK, а не сопоставление по данным.

**Номер запрашивается в сценарии оплаты, а не при регистрации.** Там же, где он нужен, показываются и требования alfabit: данные должны совпадать с данными отправителя средств в банке, 18+, лимиты.

Пароль, а не код из SMS: коды стоят денег на каждом входе, включая попытки ботов.

#### Телефон как второй способ входа — заложить сейчас, включить потом

Добавляется вторым бэкендом в `AUTHENTICATION_BACKENDS`: `USERNAME_FIELD` задаёт только способ по умолчанию, поэтому ни миграций, ни переделки сессий и cookie это не требует. Вход по номеру пускает **только при `verified_at IS NOT NULL`**. Кто зарегистрировался по почте и привязал номер, получает два входа в один аккаунт автоматически.

Две закладки делаются сразу — иначе потом миграция на живых данных:

- **`User.email` — уникальный, но `null=True`.** Появится когда-нибудь регистрация только по номеру — у такого пользователя почты не будет.
- **Номер живёт в `PhoneNumber`, а не полем на `User`.** Полем-логином он перестаёт быть отвязываемым.

Регистрация по номеру, уже привязанному к аккаунту с почтой, — не новый пользователь, а попытка дубля: блокируем и предлагаем вход.

### Подтверждение номера: ворота ставим сразу, механизм — позже

Номер при регистрации **заявительный**: пользователь вписал что угодно, никто это не проверял. Поэтому подтверждение — отдельная сущность, а не флаг на пользователе:

`PhoneNumber` — пользователь, номер, `verified_at` (nullable), `verification_method` (`max` | `telegram` | `sms` | `flashcall`).

**Реализаций каналов пока нет, `verified_at` всегда `NULL`** (решено 22.09.2026). Проверка при этом стоит с первого дня и решает, что кабинет показывает:

- **Открыто без подтверждения — то, что аккаунт создал сам под логином:** его платежи, его QR, статус KYC по номеру, который он сам и привязал. Чужого здесь показать нельзя в принципе: данные связаны с аккаунтом, а не с заявленным номером.
- **Закрыто до `verified_at` — всё, что привязывается к номеру извне.** В первую очередь исторические заказы из `Лист1`: они сопоставляются по телефону, а там ФИО, город, суммы, ТК. Чужой номер не должен показывать чужой заказ ни одного дня.

Ворота стоят сразу, чтобы включение каналов было добавлением эндпоинта, а не переделкой контроля доступа. Если их не поставить, при включении придётся решать, что делать с уже зарегистрированными непроверенными номерами — гнать всех через подтверждение задним числом или оставить им дыру навсегда.

**Номер занимает первый, кто его привязал.** Второму аккаунту с тем же номером — отказ «номер уже привязан к другому аккаунту»; забрать можно только подтверждением владения. Политика та же, что была записана для логина, но переезд на привязку сделал её безболезненной: отвязка номера больше не отнимает у человека вход.

**`expected_payer_name` (ФИО по паспорту) показывается только тому аккаунту, который сам загружал документы** — не «любому аккаунту с этим номером». `Payer` уникален по телефону и хранит верификацию, пройденную живым человеком; без этого правила привязка чужого номера превращается в способ узнать чужое ФИО. Рейт-лимит на запрос статуса KYC по IP и сессии остаётся в силе — бесплатная регистрация почты его не отменяет.

**Гостевая оплата из плана ушла** — оплата живёт в кабинете. Но эндпоинты платежа остаются безразличными к наличию аккаунта (`Payment.user` nullable), чтобы включение гостевого сценария было снятием проверки доступа, а не второй реализацией флоу. Держать его в уме стоит: людям, пришедшим по ссылке от менеджера, регистрация может резать конверсию.

**Принятый риск:** пока номер не подтверждается, его можно занять — вписать чужой номер в своём аккаунте и не дать владельцу привязать его к своему. Атака бессмысленная: занявший не видит ни ФИО по паспорту, ни заказов (оба правила выше), а владелец забирает номер подтверждением, когда каналы появятся.

### Каналы подтверждения (реализация — этап 6)

| способ | цена | комментарий |
|---|---|---|
| **MAX** | 0 ₽ | основной кандидат: сайт и MAX оба в РФ, границы нет |
| **Telegram** | 0 ₽ | бот и аудитория уже есть; ход через границу, зависит от доступности TG в РФ |
| **SMS / flash-call** | единицы рублей | последний рубеж для тех, кто не пользуется ни тем, ни другим |

Разведка по MAX (22.09.2026, [dev.max.ru](https://dev.max.ru/docs-api)): в Bot API есть кнопка `request_contact` — прямой аналог телеграмовской. Вместе с контактом приходит `vcf_info` и `hash` = `HMAC-SHA256(access_token, vcf_info)`, то есть принадлежность номера аккаунту проверяется криптографически — этого Telegram не даёт. API — `https://platform-api2.max.ru`, авторизация заголовком `Authorization: <access_token>`, бот регистрируется через `@MasterBot`. Два невыясненных условия — в «Открытых вопросах».

**Telegram Login Widget отклонён**, хотя аудитория живёт в Telegram: виджет грузит скрипт с `telegram.org`, у российских пользователей он не загрузится и кнопка входа молча не появится. Подтверждение через Telegram-**бота** этой проблемы не имеет и остаётся кандидатом.

**Восстановление пароля** — письмом на почту логина (решено 26.09.2026, вместе со сменой логина). Условие, без которого это не работает: **настроенные SPF, DKIM и DMARC на домене** плюс выбранный SMTP-провайдер — иначе письма с подтверждением и сбросом падают в спам на mail.ru и yandex, то есть у всей аудитории. Это блокирующее условие запуска кабинета, а не пожелание.

## Персональные данные — 152-ФЗ

Бот сознательно не хранит о пользователе **ничего**: `services/user_phones.py` удалён вместе с volume'ом 08.08.2026, телефоны в логах маскируются (`bot/services/kyc_trace.py` — код страны и последние 4 цифры), паспорта на диск не ложатся. Сайт с ЛК и заказами в PostgreSQL — разворот этого решения, и это уже зона 152-ФЗ.

Что из этого следует технически:

- **Фото паспорта стримятся напрямую в alfabit, не записываются ни в `MEDIA`, ни во временные файлы.** Храним только статус KYC и `expected_payer_name`. Это сохраняет главное достижение бота.
- **nginx нельзя оставлять с настройками по умолчанию на эндпоинте загрузки документов.** `client_max_body_size` по умолчанию 1 МБ — фото паспорта отобьётся с 413 (бот пропускает до 20 МБ). Важнее другое: при `proxy_request_buffering on` (значение по умолчанию) nginx сначала целиком пишет тело запроса во временный файл на диск и только потом отдаёт его Django — то есть паспорт всё-таки окажется на нашем диске в обход гарантии выше. На этом эндпоинте буферизацию запроса выключаем, а `client_body_temp_path` выносим на tmpfs.
- Телефоны в логах — только маскированные, переносим `mask_phone()` как есть.
- БД и бэкапы — на российских серверах, бэкапы шифруются.
- Доступ в админку — только по 2FA, список сотрудников минимальный.

Что следует организационно (не код, но без этого запускать нельзя): оферта, политика обработки персданных, явное согласие чекбоксом перед загрузкой документов, уведомление РКН об обработке.

| Бэкенд | Django 5 + DRF | админка — главная причина выбора Django |
| БД | PostgreSQL 16 | |
| Фронтенд | Nuxt 3 (Vue 3, SSR/ISR) | пороутный рендеринг, см. ниже |
| Фоновые задачи | отдельный контейнер `worker`: Django ORM + APScheduler | **без Redis и Celery** |
| Сервис курсов | FastAPI + SeleniumBase + Chromium + APScheduler | отдельный репозиторий/контейнер, за границей |
| Кеш | PostgreSQL + локальный in-memory | Redis не нужен |
| Контейнеризация | Docker + docker-compose | |
| Веб-сервер | nginx + certbot | TLS продлевается по cron, не сам; настройки под загрузку документов — см. 152-ФЗ |

**Почему `rate-service` отдельно.** Не «потому что микросервисы», а из-за investing.com: это headless Chromium, 2–3 минуты на вызов, `ThreadPoolExecutor(max_workers=1)`, watchdog с убийством осиротевших процессов и жёсткий таймаут 420 с (`bot/services/rate_providers/investing.py`). Держать такое внутри gunicorn нельзя. Rapira и alfabit — это два HTTP-запроса, сами по себе они отдельного сервиса не требуют, но едут туда же за компанию: один источник котировок на бота и сайт.

**Почему без Celery.** Фоновой работы ровно три вида: обновление курсов, опрос статусов платежей, опрос заявок KYC. Всё — простые периодические задачи без цепочек и приоритетов. APScheduler в отдельном контейнере с загруженным Django ORM закрывает это без Redis. Celery добавляем, когда понадобятся ретраи с видимостью и очередь задач, а не «потому что Django».

### Рендеринг: пороутно

Чистый SPA провалил бы SEO каталога (люди ищут эндуро в Москве поиском), а Django-шаблоны превратили бы флоу оплаты с KYC, поллингом и загрузкой файлов в мучение. Nuxt закрывает обе половины одним кодом:

```ts
routeRules: {
  '/':            { prerender: true },
  '/catalog/**':  { isr: 600 },      // SSR + кеш, обновляется после правки в админке
  '/rate':        { ssr: true },     // цифра в HTML для поиска, дальше живёт на клиенте
  '/account/**':  { ssr: false },    // обычный SPA, в HTML ничего не утекает
  '/checkout/**': { ssr: false },
}
```

Цена решения, принятая осознанно: +1 контейнер с Node; SSR-дисциплина (никаких `window` / `localStorage` на верхнем уровне модулей); **авторизация через httpOnly-cookie, а не JWT в localStorage** — при SSR сервер рендерит страницу от имени пользователя и до localStorage не дотянется. Побочно это и безопаснее: токен в localStorage выносится первой же XSS.

## Источник истины по цене

Ключевое решение, из которого растёт половина архитектуры.

- **`rate-service` отдаёт только сырые котировки** — `usdt_rub_raw`, `usd_rub_raw`, `alfabit_showcase` (уже с комиссией метода, она часть котировки, а не наценка) и `fetched_at`. Никакой бизнес-логики, никаких наценок.
- **Django владеет наценками и делителем 6.63**, хранит их в БД, правятся в админке, считает итоговую цену и публикует `GET /api/v1/pricing/`.
- **Бот позже переключается на этот же эндпоинт** вместо собственной математики (этап 8). До этого момента бот и сайт считают независимо, и правка наценки в админке на бота не влияет — это временное расхождение, принятое сознательно.

Иначе первая же правка ползунка в админке разведёт цены бота и сайта в тот же день.

## Каталог: переходный период

Сайт — на админке, бот пока на Google Sheets (решено). Это значит, что один и тот же байк ведётся в двух местах и рано или поздно про одно из них забудут.

**Смягчение (выбрано):** на старте Django импортирует `Лист2` по таймеру **односторонне** (Sheets → БД), редактирование каталога в админке до переключения выключено. Менеджер работает как привык. Мастер переключается одним днём, когда сайт готов. `bot/services/sheet_reader.py` и `catalog_cache.py` переиспользуются почти целиком.

**Двусторонняя синхронизация Sheets ↔ БД отклонена** — в обозримом будущем к ней не возвращаться.

Код бота хороший: комментарии объясняют *почему*, а не *что*, и все грабли уже пройдены. Переносить вместе с комментариями, не «причёсывая».

- `services/rate_providers/*` — целиком в `rate-service`.
- `services/yuan.py`, `services/usd_markup.py` — как основа для расчёта, но значения переезжают в БД.

- `utils/phone.py`.

**С изменениями:**

- `KycWatcher` — реестр из памяти переезжает в таблицу, наблюдение переживает рестарт. Потолок 72 часа сохраняем.
- Логика «протухших» данных из `handlers/rates.py` — переезжает в сериализатор.
- Поллинг платежа — из кнопки «Я оплатил» в фоновую задачу `worker` + опрос фронтом нашего API.

### Копия клиента alfabit, а не общий пакет

Соблазн сделать общий `enduro-core` для бота и сайта есть, но реализации разойдутся сразу: у сайта настоящий IP плательщика, вебхуки, состояние в БД. Общий пакет на одного разработчика — постоянная стоимость синхронизации двух деплоев ради экономии, которой нет. Копируем и развиваем отдельно.

## Несоответствия в боте, которые надо решить, а не перенести

1. **VIP-окно не реализовано.** `get_usd_rate_info()` проверяет только выходной/будний день. Никакой проверки времени там нет, при этом бот пишет «VIP курс действует с 12:30 до 16:00 в будний день» и тут же показывает VIP-уровни в любое время. Либо текст врёт, либо логика не дописана. На сайте моделировать явно: у тарифного уровня есть окно действия (дни недели + интервал времени), и вне окна он не показывается.
2. **Строка «Курс (юань/руб): — 6.63»** показывает делитель, а не курс. Люди путаются. На сайте так не писать.

`rate-service` лежит в этой же репе, но **деплоится отдельно**: свой Dockerfile, свой `docker-compose.yml`, своя машина и своя страна. ## Этапы

1. ✅ **Каркас.** Репозиторий, docker-compose (Django + PG + Nuxt + nginx + worker), модели, админка, пустой Nuxt, который уже ходит в API.
2. ✅ **`rate-service`.** Перенос `rate_providers/*` как есть, `GET /rates`, Chromium в своём образе, деплой за границу.
3. ✅ **Курс на сайте.** `worker` тянет котировки, `pricing` применяет наценки из БД, `GET /api/v1/pricing/`, публичная страница курса. **Здесь уже можно показывать клиенту.**
4. **Личный кабинет.** Регистрация почта + пароль, подтверждение почты письмом, сброс пароля, привязка номера. Кабинет показывает только то, что аккаунт создал сам. Заложить сразу: `email` уникальный и `null=True`, номер — в `PhoneNumber`, место под второй бэкенд аутентификации.
5. **Оплата внутри кабинета.** Alfabit с настоящим `payer_ip`, KYC со стримингом фото мимо диска, состояние в БД, фоновый опрос статусов. `expected_payer_name` — только тому, кто сам загружал документы, и только на шаге QR; на обращения к `get_payer` rate-limit по IP и сессии. Уведомление менеджеру о заявке.
6. **Заказы и подтверждение номера.** Импорт заказов из Sheets, история и статусы поставки в кабинете — **открываются каналами подтверждения**, без `verified_at` заказы по номеру не показываются. Здесь же номер включается вторым способом входа.
7. **Каталог**: переключение мастера со Sheets на админку.
8. **Бот → API.** Бот переключается на `/api/v1/pricing/`, дальше — на каталог и заказы из БД. Одна точка истины.

## Отклонённые подходы (не реализовывать, если не попросят явно)

- **Чистый Vue SPA без SSR** — проваливает SEO каталога и страницы курса.
- **Django-шаблоны + Vue-виджеты** — дешевле, но с ЛК, KYC и флоу оплаты получаются две системы вёрстки с дублированными стилями.
- **Telegram Login Widget** — скрипт с `telegram.org` не загрузится у российских пользователей. Подтверждение через Telegram-бота — другое дело, оно остаётся кандидатом.
- **Телефон как логин** — было решено 22.09.2026, отменено 26.09.2026: номер нечем подтвердить бесплатно, а неподтверждённый логин закрывает кабинет целиком. Логин — почта, см. «Личный кабинет». Сам номер остаётся ключом KYC и позже становится вторым способом входа.
- **Заявительный номер как ключ доступа** — номер из формы без подтверждения не открывает ни исторические заказы, ни ФИО по паспорту из чужого KYC. Никогда.
- **Гостевая оплата как отдельный флоу** — не реализовывать второй раз. Оплата живёт в кабинете, а эндпоинты остаются безразличными к наличию аккаунта: понадобится гостевой сценарий — это снятие проверки доступа.
- **Готовые сервисы авторизации через MAX** (Auth4App и подобные) — номер пользователя пошёл бы через третью сторону, то есть обработка ПД сторонним лицом: договор поручения по 152-ФЗ и строчка в политике. Свой бот дешевле и чище.
- **JWT в localStorage** — несовместимо с SSR и выносится первой XSS. Только httpOnly-cookie.
- **Celery + Redis** — избыточно для трёх периодических задач. Порог пересмотра — ниже.
- **Двусторонняя синхронизация Google Sheets ↔ БД.**
- **Общий пакет кода между ботом и сайтом.**
- **Синхронный вызов `rate-service` из запроса пользователя.**
- **Хранение фото паспорта на нашей стороне.**

## Открытые вопросы

- **Список методов оплаты у alfabit пуст — на их стороне.** `GET /wallet-web/api/v1/public/buy-sell/banks/RUB` отвечает HTTP 200 и `{"data": []}` (наблюдается с 22.09.2026, подтверждено 26.09.2026: конвертер у них отвалился). Оттуда берётся комиссия метода `SBPRUB`, без неё курс витрины не считается, и строка «QR + KYC» не показывается — поведение верное, посчитать без комиссии значит тихо уронить цену на 1.8%. С нашей стороны делать нечего; после первого успешного чтения комиссия ляжет в память провайдера и переживёт следующее такое падение. Аварийный клапан `ALFABIT_FEE_PERCENT_FALLBACK` (комиссия от оператора вручную) остаётся выключенным по умолчанию: зашитая комиссия перестаёт ехать за кабинетом. **Задевает и бота в проде** — при перезапуске во время такого падения строка QR+KYC пропадёт и у него.
- **Есть ли у alfabit вебхук на статус платежа.** На KYC точно нет. Если на платёж есть — фоновый опрос в `worker` становится страховкой, а не основным механизмом.
- **Нужен ли поисковый трафик на самом деле.** Весь выбор в пользу SSR держится на этом. Если люди приходят только по ссылке из Telegram-канала и от менеджера — Nuxt SSR лишний, и решение стоит пересмотреть до этапа 1.
- **SMTP-провайдер не выбран, SPF/DKIM/DMARC на домене не настроены.** Пришло на критический путь вместе со сменой логина на почту: без доставляемости на mail.ru и yandex не работают ни подтверждение адреса, ни сброс пароля, то есть не запускается кабинет. Нужно к этапу 4. Подстраховка на первое время — сброс пароля руками менеджером из админки, при текущих объёмах вариант рабочий.
- **MAX: допустят ли к регистрации бота.** По имеющимся данным, с августа 2025 создавать ботов могут только российские юрлица, ИП и самозанятые — физлицам отказывают. Нужен к этапу 6, не раньше.
- **MAX: правила использования номера.** Есть указание, что данные из `request_contact` предназначены для взаимодействия с этим же ботом. Наш сценарий в формулировку вроде укладывается, но границу надо прочитать в их правилах глазами до того, как строить на этом подтверждение.
- **SMS-провайдер не выбран**, имя отправителя не зарегистрировано. С критического пути ушло — нужен к этапу 6, и только если MAX и Telegram не закроют вопрос.
- **Как уведомлять менеджера о заявке.** `MANAGER_TG_CHAT_ID` в `.env` есть, кода нет, и напрямую он не заработает: `api.telegram.org` из РФ недостижим — по той же причине, по которой бот живёт за границей. Варианты: реле через зарубежный узел (бот или машина `rate-service`) либо другой канал (MAX, почта). Нужно к этапу 5: заявка на оплату без оповещения менеджера бессмысленна, юань выдаёт человек.
- **Юридический пакет** (оферта, политика ПД, согласие, уведомление РКН) — не начат. Со сменой логина на почту добавился адрес как персональные данные — режим обработки тот же, но в политике он должен быть перечислен.
- **Что показывать в ЛК по заказам** — весь набор колонок из Sheets или урезанный.
- **Судьба колонки `Прог-я`** в листе заказов — назначение до сих пор не выяснено (висит открытым и в боте).

## Порог пересмотра архитектуры

- **Redis + Celery** — когда фоновых задач станет больше трёх видов, понадобятся ретраи с видимостью или очередь пользовательских задач.
- **Выделенный поиск (OpenSearch)** — когда каталог перестанет искаться `ILIKE` по паре сотен позиций.
- **Отдельный сервис платежей** — когда появится второй эквайер помимо alfabit.

До этих порогов — не реализовывать.
